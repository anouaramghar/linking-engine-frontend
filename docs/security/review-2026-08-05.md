## Threat surface

The browser handles WordPress credentials, site configuration, suggestion decisions, pool approvals, and publication controls. It calls same-origin `/api/v1`; Vite/nginx then injects one shared backend API key. There is no user/session/role concept in the SPA. Sensitive sinks include site deletion, crawls, analysis jobs, reviews, pool approval, and live WordPress publication.

## Deduplicated candidate ledger

### FE-SEC-01 — Shared-key proxy grants every dashboard caller full backend authority

- Severity: **High when network reachable**; lower in an enforced single-user loopback deployment.
- CWE: **CWE-306 — Missing Authentication for Critical Function**
- Source/exposure: `nginx.conf:1-3`; the documented command does not constrain Docker publishing to loopback, `README.md:61-67`.
- Broken control: nginx adds `X-API-Key` to every `/api` request, `nginx.conf:22-29`; all SPA routes render without authentication, `src/App.tsx:81-169`.
- Backend boundary: the only protected-router identity is that shared key, `linking-engine-backend/app/main.py:8-18` and `app/api/deps.py:19-26`.
- Sinks: site and publication mutations at `src/api/sites.ts:39-64`; review and job mutations at `src/api/suggestions.ts:91-92,136-150,192-238`.
- Reachability: a caller that can reach the dashboard needs no key; the proxy supplies it. They can create/delete sites, enqueue expensive work, change review state, and publish approved links.
- Counterevidence/proof gap: an authenticated outer proxy, VPN, or enforced loopback-only binding may be part of deployment but is not present or documented here.
- Disposition: **Reportable, cross-cutting**. Deduplicate against any backend authentication finding.
- Fix: enforce real end-user/role authentication at the edge or backend. Keep the shared key solely as a proxy-to-backend credential; a frontend-only login gate is not authorization.

### FE-SEC-02 — Authenticated proxy lacks Host/origin/CSRF boundary

- Severity: **Medium**
- CWE: **CWE-352**, with a **CWE-346** Host/origin-validation aspect.
- Source: nginx accepts arbitrary hosts through `server_name _`, `nginx.conf:1-3`.
- Broken control: `/api` requests receive the shared key without Host, Origin, CSRF-token, or custom-header validation, `nginx.conf:22-30`.
- Confirmed bodyless POST sinks:
  - ingestion: `linking-engine-backend/app/api/routes/ingestion.py:19-35`
  - analysis/comparison: `app/api/routes/suggestions.py:480-505`
  - publication: `app/api/routes/publish.py:48-59`
- Reachability: these endpoints do not require JSON bodies, so a cross-origin HTML form can submit them without reading the response. The wildcard host also leaves a DNS-rebinding path unmitigated.
- Preconditions: victim dashboard running, a known/guessable site ID, and browser/network behavior permitting the request.
- Counterevidence/proof gap: Private/Local Network Access browser controls, DNS pinning, or an outer proxy may block some loopback paths; no browser exploit was run.
- Disposition: **Reportable Medium for loopback/trusted-network deployments**. When directly network reachable, FE-SEC-01 already supplies the simpler attack path.
- Fix: allowlist Host, reject foreign Origin on unsafe methods, require an anti-CSRF/custom header, and bind local deployments explicitly to loopback.

### FE-SEC-03 — Documented production path can transmit WordPress credentials over HTTP

- Severity: **Medium, deployment-dependent**
- CWE: **CWE-319 — Cleartext Transmission of Sensitive Information**
- Source: WordPress username/application password entry, `src/components/sites/AddSiteModal.tsx:132-174`.
- Flow: submission includes credentials, `AddSiteModal.tsx:42-61`, then POSTs through `src/api/sites.ts:39-40` and the same-origin client at `src/api/client.ts:5-8`.
- Transport: nginx listens on plain HTTP, `nginx.conf:1-2`; the “Production container” example publishes port 80 and instructs an HTTP URL, `README.md:50-67`.
- Impact: a network observer or active intermediary could recover reusable WordPress application credentials.
- Counterevidence/proof gap: localhost access or an external TLS terminator prevents this; neither production TLS nor trusted-proxy requirements are documented.
- Disposition: **Reportable deployment/documentation finding** if this is the supported production path.
- Fix: make production HTTPS/TLS termination mandatory and change the local command to `-p 127.0.0.1:8080:80`.
